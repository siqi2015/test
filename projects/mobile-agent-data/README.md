# 主动服务 agent：记忆使用的数据评测、筛选与合成

最近更新：2026-11-03（Asia/Shanghai）。当前阶段：记忆数据标准与入门方案讨论。当前建议先读本文，再看 [入门流程与具体例子](architecture-and-technical-options.md)。

**1. 当前目标与分工**

我们当前负责围绕“记忆是否被正确理解和使用”准备评测与训练数据，支持合作方主动服务 agent 更符合用户需求和喜好。训练基础设施和训练算法由其他同事配合。数据标准、筛选与合成实现、数据质量检查、评测样例和错误分析是当前工作的重点。

| 参与方 | 当前职责 |
| --- | --- |
| 合作方 | 主动服务 agent 本体、OpenClaw 改造、已有 skills 和实际记忆／执行系统 |
| 我们 | 记忆使用的评测数据与判定标准、数据筛选与合成、来源与版本管理、交付及错误分析 |
| 训练同事 | 训练基础设施、训练算法与训练运行；与我们对齐输入格式，提供模型评测输出或共同评测 |
| 协作边界 | 我们给出样本、任务和检查依据；模型如何更新、奖励如何接进训练、运行环境如何部署，由相关同事负责或另行明确 |

用户提供的背景：agent 基于深度修改的 OpenClaw，内部有 skills；目标包括主动发现需求、执行任务、夜间内容挖掘与推送，产品对标对象按用户称呼记为 Meta“muse”。具体实现代码和真实数据尚未取得，对标细节也未独立核验。

先前的全流程方案保留为参考。当前将记忆置于数据工作的中心，不再把训练框架选型、RL 算法实现或完整交互环境建设作为我们的起步任务。此为用户当前明确分工，后续可随协作变化调整。

**2. 先评估四种记忆使用能力**

| 能力 | 想知道什么 | 典型错误 |
| --- | --- | --- |
| 判断相关性 | 哪些记忆能支持当前服务，哪些无关 | 忽略有关偏好，或强行使用无关记忆 |
| 理解含义与适用范围 | 是稳定偏好、临时要求、过去事件，还是不确定推断 | 把一次行为当长期偏好，把工作日要求套到所有场景 |
| 处理变化和冲突 | 哪条记录仍有效，哪些有条件、已完成或被明确更新 | 使用已失效信息；机械认为时间最新的一条永远正确 |
| 转化为恰当服务 | 内容、动作、时间是否符合记忆支持的需求 | 引用了正确记忆却作出不合适的推荐、重复推送或时机错误 |

先把一份候选记忆直接放入样例，评估“看到了以后是否会用”。后续取得真实接口后，再区分完整记忆库里有无相关信息、检索是否找出、模型最终是否看到以及看到后是否用对。当前给定记忆的结果不能当作端到端检索效果。

记忆提取、写入、更新和删除也可能影响结果；当前保留为待核验环节，不在没有实现依据时自行增加整套记忆系统建设。

**3. 一条样例先理解为五个部分**

| 部分 | 需要写清楚的内容 |
| --- | --- |
| 当前情境 | agent 在什么时间、准备提供什么服务，当时可见哪些信息 |
| 可用记忆 | 每条记忆的内容、ID、来源和适用时间；事实、明确偏好和推断要能区分 |
| 候选表现 | agent 的实际或候选动作／回复；是否已执行要明确 |
| 判断依据 | 哪些记忆相关，哪些选择可接受，哪些行为违反约束，依据来自哪里 |
| 来源与状态 | 真实记录／公开转换／合成，父案例、用途切分、审核状态及生成版本 |

标签侧的参考判断不能泄漏给被评测模型。内部推理、检索过程和执行结果未提供时，不补造。候选表现没有运行证据时标为生成候选，不能写成真实 trace。

具体虚构例子见入门文档。初期允许表格人工查看、JSONL 程序读取；不需要先设计庞大 schema。

**4. 当前只沿一条数据流程推进**

```text
明确“怎样才算用对记忆”
  → 建立可逐条核验的种子案例，并划分开发／训练来源与独立评测来源
  → 收集或生成候选表现
  → 筛选：检查依据、行为和记录是否合格
  → 合成：围绕覆盖缺口构造记忆与情境变体
  → 再核验，形成有版本的数据包
  → 训练同事使用，双方按固定评测样例回查错误
```

目前没有真实 agent 输出，所谓“典型错误”是设计要覆盖的风险，尚不是已经观察到的模型失败。可以先用明确标记的合成情境制定标准；真实样本到达后再检查贴近程度。

**5. 筛选与合成各负责什么**

筛选是判断已有或已生成的样例是否可用、适合什么用途，并记录原因。至少检查：决策输入完整；关键记忆当时可用；行为符合记忆含义和约束；未把猜测写成用户事实；输出和依据不矛盾。难以判断的样例保留为待复核。

合成是补齐当前缺少的学习场景。先围绕同一案例做可解释的变化：更新有效偏好、增加已完成记录、移除关键证据、加入无关干扰。变化是否应改变行为要预先说明，再生成候选并核验。必要时重新定义标签，不能沿用变更前的答案。

筛选合格后才进入相应训练视图。失败和被排除记录保留，可用于错误分析或经核验的比较样本；不能默认全部作为正面示范。合成标签在虚构设定内成立，不等于真实用户满意度。

**6. 给训练同事的三类交付**

| 交付物 | 内容 | 用途边界 |
| --- | --- | --- |
| 独立评测集 | 记忆、情境、检查标准、可接受结果与来源 | 比较训练前后；最终测试来源不用于合成训练数据或调规则 |
| SFT 示范数据 | 记忆和情境 → 经验证的动作／回复，保留依据与审核信息 | 具体工具格式和被训练的输出部分与训练同事对齐；原始记录不被训练格式覆盖 |
| RL 候选任务与评价规格 | 初始记忆／情境、决策目标、可检查条件与失败定义 | 没有执行接口时只是任务规格；环境运行与训练奖励接线由同事协作完成，不能称为已可直接运行的 RL 数据 |

另附数据版本、来源比例、能力覆盖、筛选原因与已知局限。偏好对有明确需要且能构造可比候选时再提供，不作为首批必须产物。

**7. 起步技术与判断方法**

第一版使用可人工查看的表格、JSONL 和简单 Python 处理即可。人工核对小批种子案例，规则检查结构与引用，模型辅助生成和语义初审。模型的自评分不能单独证明样例正确；不确定项要能回到证据核查。

引用了记忆 ID 不等于真正用对：应同时看行为是否符合依据，关键记忆变化后是否合理调整，无关信息变化时是否保持稳定。指标先分别报告相关性、更新／冲突处理、行为符合度和证据不足时的处理；错误标签仍需核验。

初期评测开发集用于校准规则和生成策略；独立测试集用于阶段评价。共享原始故事、用户历史或变体家族的样例不要拆到训练和测试两侧。保存全部允许保留的原始记录，统计说明分母和排除原因。

**8. 最容易上手的第一阶段**

建议先产出一张小样例表：围绕“夜间为用户准备阅读推荐”，包含正常使用偏好、偏好有适用条件、已有交付、缺少依据与无关记忆干扰等情况。起步可用约 20 条逐条核验，规模根据分歧和覆盖情况调整。先确认为什么应该接受或排除，再实现最简单的读写、检查和分流。

接着只做一类受控变体，例如“已交付／未交付”，检查生成后答案是否随条件正确改变。标准能稳定使用后再扩展场景和数量，并与训练同事做小批数据交付。真实训练收益需要训练与独立评测反馈，不能仅以筛选通过率或数据量证明。

这条路线可借鉴用户熟悉的 skill 自演进流程：收集案例、识别不足、生成候选、验证保留。这里沉淀的是有依据的样例和检查标准，后续由训练同事用于模型能力增强。

**9. 后续逐步核验的问题**

1. **目标能力与行为样例**：记忆理解与使用已明确为重点；当前建议以阅读推荐样例起步，之后用真实场景校正。
2. **现有数据**：记忆的原始形态、来源、更新时间、模型实际可见内容及 trace 关联仍未知。先允许合成样例，明确标记来源。
3. **结果与环境**：哪些行为可从记忆与情境判定，哪些必须取得工具状态、展示记录或用户反馈才能判断；不能把规则符合等同于真实满意。
4. **下游接口**：训练基础设施和算法由其他同事负责；后续只需对齐数据字段、输出格式、评价规格和反馈方式，不由我们先选训练框架。
5. **运行条件**：真实数据的可保存范围、标注与模型调用条件待明确；当前不阻塞标准、例子和方案讨论。

以上无需用户现在一次答齐。优先把样例与判定标准讲清楚，再随真实材料补充。
